# 无名杀避坑清单

> 来源：王朗（CHEN 005）实战过程中真实发生过的问题 + 代码复查发现的隐患。
> 用途：① 人写武将时对照；② **作为 AI 生成武将时的硬性约束**（工坊的提示词会引用本文）。
> 原则：**只写实证过的**。推测的标「待确认」，不写成结论。

## 零、不报错的易错点（最难查）

> 这一节的共同点是：**技能能发动、框也弹了、也选了，然后什么都没发生**，或者「效果正常但标记不显示」。
> 没有异常、没有日志 —— 只能靠知道它存在才查得出来。
> 下面每一条都回引擎源码核对过；标「实测」的是第三方跑出来的症状，未见反例。

### 0.1 `forResult()` 返回的就是 result 本身，**不要解构**

```js
const { result } = await player.chooseControl(["a","b"]).forResult();  // 错：result.result 恒 undefined
const result = await player.chooseControl(["a","b"]).forResult();      // 对
```

引擎里 `forResult()` 就是 `await this; return this.result;`。解构后 `result` 是 `undefined`，
代码在 `if (!result) return;` 那一步直接返回。详见 `无名杀技能系统.md` 开头「三个易错点」第 1 条。

### 0.2 事件 `content` 一律写 `async`

```js
content(event, trigger, player) {}        // 错：被当成旧式 step content，用 new Function 重编译
async content(event, trigger, player) {}  // 对
```

重编译后**模块作用域全丢**，文件顶部定义的函数/常量全变 `undefined` → `ReferenceError: xxx is not defined`。
**同一个文件里主技能写了 async、子技能漏写 → 只有漏写的那个崩**，很容易误判成"引擎有问题"。
（`intro.content` / `translate` 里的 `content(storage,…)` 是 UI 用的，不受此限。）

### 0.3 `gaintag` 不加 `eternal_` 前缀，牌一移动就被清

引擎在牌移动处执行 `gaintag.filter(tag => !tag.startsWith("eternal_"))` 然后删掉它们。
**症状**：牌面标记「只在当回合可见」。
`eternal_` 不会自动过期，效果结束要自己 `removeGaintag`；翻译键照**全名**写（`eternal_xxx: "酒"`）。

### 0.4 借来的官方技能可能依赖「引擎为原主人准备的上下文」（实测）

技能被「借用/转移」（如化身类的 `addAdditionalSkills`）之后，原先由原主人调用链带进来的
`event.targets` / `event.cost_data` / `event.getParent(n)` 层数 / `event.name` 拼出的子技能名
**可能全都不在了**，于是子技能一触发就 `Cannot read properties of undefined`。

要复用官方技能，先确认它读不读这些上下文；读就得补齐，补不齐就换写法。

### 0.5 `mod.*` 与 `filterCard` 的入参**不一定是实体牌**（实测）

`get.judgeSlots()` 之类会把字符串转成 `{ name: obj }` 这种**纯对象**再往下传，于是
`card.hasGaintag(...)` 直接 `TypeError: card.hasGaintag is not a function`。
防御写法：

```js
function hasTag(card, tag) {
    return !!card && typeof card.hasGaintag === "function" && card.hasGaintag(tag);
}
```

### 0.6 视为技不写 `ai.respondShan` / `respondSha`，AI 不会来响应

把一张牌"当作【闪】/【杀】/【桃】使用"的技能，如果只写了 `viewAs` 而没写对应的
`ai.respondShan` / `respondSha` / `respondTao` / `save`：

- **AI 操控这个武将时**，它只检查手牌里有没有真【闪】/【杀】。没有 → **直接放弃响应**，
  哪怕技能完全能救它。表现为"AI 站着挨打"。
- **玩家手操完全不受影响**（这条是纯 AI 侧的问题，所以调试时不写也测不出来）。

```js
ai: { respondShan: true },   // 一句话的事
```

同类还有：免疫类技能不写 `nofire` / `nothunder` / `nodamage` 等 → AI 重复做无效动作、白浪费牌。

详见 `无名杀技能系统.md` 第 3.5 节「`ai`：什么时候该写」。

## 一、已真实发生的 bug

### 1. 游戏直接崩溃：`Cannot set properties of null (setting 'innerHTML')`

| 项 | 内容 |
|---|---|
| 症状 | 游戏错误框 `TypeError: Cannot set properties of null (setting 'innerHTML')` |
| 位置 | 引擎 `noname/library/element/card.js:853` → `node.node.gaintag.innerHTML = ""` |
| 触发链 | `chooseToCompare` → `$compare`（拼点翻牌动画）→ `card.copy()` |
| 根因 | 引擎的 `card.copy()` **硬编码假设**每张卡的 DOM 里必有 `.gaintag` 子节点并对它直接写 `innerHTML`；第三方皮肤（实测触发者是某个 UI 皮肤扩展 的拼点动画链）会移除该节点或其 class，于是取到 `null` 就抛错 |
| 归属 | **引擎隐式契约 + 第三方皮肤兼容问题**，不是扩展写错 |
| 修法 | 扩展侧 monkey-patch：调用原 `copy` 前先补一个空 `.gaintag` 节点；用幂等标记防止重复包装 |
| 官方版本 | 同样的写法在官方 v1.11.6 的 `card.js:895` 依然存在 —— **换版本不会自动免疫** |

**教训**：引擎中凡"假定某 DOM/字段必然存在"之处，扩展一旦触发此前无人走过的路径（拼点动画 + 第三方皮肤即属此类），即抛错。
**对策**：不依赖未文档化的 DOM 结构；确需修正引擎行为时，用**扩展侧防御性补丁 + 幂等标记**，并写明原因。

---

### 2. 锁定技不锁定：技能会先询问玩家

| 项 | 内容 |
|---|---|
| 症状 | 辞锋写着"锁定技"，实战中却弹出询问，玩家可以拒绝发动 |
| 根因 | 漏写 `forced: true`。`locked` 只影响 UI 上的「锁定技」标签，**是否强制发动由 `forced` 决定** |
| 修法 | 补 `forced: true` |
| 验证 | 规则集专题一：锁定技标签与是否强制**无关**，关键看描述里有没有「可」字 |

**教训**：**技能类型是靠字段表达的，不是靠描述文字**。漏一个字段，语义就变了，而且静态检查看不出来（能跑、不报错，只是行为不对）。
**对策**：把技能类型字段列成必填清单，写完逐个对照（见第三节）。

---

### 3. 显示名不符合官方约定：`王朗` 应为 `族王朗`

| 项 | 内容 |
|---|---|
| 症状 | 卡面/选将显示「王朗」，与官方同族武将风格不一致 |
| 根因 | 宗族武将的官方命名约定：显示名带宗族前缀（官方 `clan_wangling` → 「族王凌」） |
| 修法 | `translate` 的显示名改为「族王朗」 |

**教训**：命名约定不看引擎源码是发现不了的，官方同族武将就是标准答案。
**对策**：写宗族武将前，先在引擎里找一个同类武将，**参考它的命名/字段风格**。

## 二、代码复查发现的隐患（值得防）

### 4. 技能被移除时，`storage` 里的牌会永久丢失 [警告]

`chen_cifeng` 把移出游戏的牌记在 `player.storage.chen_cifeng`，
`onremove` 里直接 `delete player.storage.chen_cifeng`。

**问题**：那些牌此刻还在 `ui.special`（游戏外）。技能一旦被移除（断念、夺锐之类），
`delete` 即丢失引用 —— **牌永久丢失**，等同于凭空消失数张牌。

**建议**：`onremove` 应该「归还」而不是「删除」——把 storage 里的牌放回弃牌堆，再清空。

**教训**：`init`/`onremove` 成对只是及格线；**onremove 里的清理要区分"可丢弃的状态"和"必须归还的资源"**。

---

### 5. `result.bool` 在平局时的取值 — 待确认

文伐用 `if (result.bool)` 判断"赢"，注释写「没赢（含平局）」。
但引擎里同时存在 `result.tie` 字段（`clan/skill.js:1640` 附近）；

**注意平局分支**：`result.tie` 与 `result.bool` 同时存在，判断时要显式处理平局 ——
只写 `if (result.bool)` 的话，平局若仍置 `true`，文伐就会走错分支（本该失去体力，却去用牌）。

**教训**：**结果对象里有多字段时，不要用其中一个字段默默承担全部语义**。宁可写 `if (result.bool && !result.tie)` 把意图写明。

---

### 6. 引擎 API 的参数语义不能想当然

文伐里两处调用值得复核：

- `player.canCompare(target, goon)` —— 第二个参数的真实语义要对着源码读，注释里"有中央区可借牌时无视手牌不足"是**推断**，待确认
- `chooseCardButton(prompt, cards, true)` —— 第三个参数的语义同样要核实（是否表示强制）

**教训**：参数语义不可凭名称推断。**每个传了参数的位置，都要在引擎源码里找到定义处读一遍**。

---

### 7. 新版引擎特性没做防御性检测

用到 `_status.discarded`、`clans`、`clanSkill`、`player.hasClan` 等（已确认官方 v1.11.6 存在）。
但如果把扩展发给**旧版本客户端**，这些字段可能不存在 → 技能初始化即崩。

**建议**：对外分发的扩展，关键特性做一次存在性检测 + 优雅降级（例如中央区为空时不做转换）。

---

### 8. 主动技里读 `cost` 的数据全是 undefined，而报错指向别处

- **现象**：主动技（`enable` 型）写了 `async cost(...)`，在里面选好了选项 / 牌 / 目标；
  `content` 里读 `event.cost_data` / `event.targets` / `event.cards` **全是 undefined**，
  但 `event.result.bool` 是真的 → `content` 照常往下跑，直到读字段那一行才炸：
  ```
  TypeError: Cannot read properties of undefined (reading 'option')
      at GameEvent.content (…/character/character.js:1312:35)
  ```
  报错位置指向"读字段"，**看不出真因**（实际发生过连改两遍才找到）。
- **真因**：`cost` 只在**触发技**路径里创建（`createTrigger`，`content.js:4117` 附近）；
  主动技走 `chooseToUse`（`content.js:5091` 起），那条路根本不碰 `cost`。详见规范 6.9。
- **怎么办**：主动技的"发动前询问"用 `precontent`；跨阶段传数据用 `player.storage`。

### 9. 判"这张牌造成了伤害"不能用对象相等

- 用 `get.autoViewAs(...)` 造的**虚拟牌**，与引擎伤害事件里那张**不是同一个对象**，
  `evt.card === card` 永远不成立 → 明明打中了也走"没造成伤害"分支。**不报错，行为是反的**。
- 正解是比较**增量**：
  ```js
  const before = player.getHistory("sourceDamage").length;
  await player.useCard(card, target, false);
  const hit = player.getHistory("sourceDamage").length > before;
  ```

### 10. 时机名 `discard` 看着能用，官方统一写 `discardAfter`

- `trigger: { global: "discard" }` 引擎不报错、也**不会触发** —— 静默失效。
  官方先例一律写 `discardAfter`（`diy/skill.js:8155` 的 `nsjihui`，
  它的 `event.cards` 就是"本次被弃置的牌"）。
- 这类"猜时机名"的错误一条报错都不会有，只能依靠**查官方先例**发现。

### 11. `_status.discarded` 不等于"被弃置的牌"

- 它是**本回合进入弃牌堆的所有牌**：使用后落堆的、打出的、重铸的、被置入弃牌堆的**全在里面**
  （回合切换时清空：`content.js:3350` / `:4750`）。
- 描述写"获得被弃置的牌"而实现读 `_status.discarded`，口径就对不上 —— 作者一眼看得出来。
  真要"被弃置的牌"，听 `discardAfter`（见上一条）。

## 三、根因分类（写代码时按这个顺序自查）

| 类别 | 典型表现 | 自查动作 |
|---|---|---|
| **A. 引擎隐式契约** | 崩在引擎内部某行 | 不假设 DOM/字段存在；需要时防御性补丁 |
| **B. 技能类型字段** | 行为与描述不符（不强制、不静默） | 逐个核对 `locked`/`forced`/`clanSkill`/`silent`/`charlotte` |
| **C. 官方命名约定** | 显示名、id 风格不对 | 找同类官方武将参考 |
| **D. 资源生命周期** | 牌/状态丢失或跨局残留 | `init`/`onremove` 成对；区分「丢弃」与「归还」 |
| **E. 结果与边界** | 平局、无牌、无目标、角色已死 | 把边界写成显式的 `if`，不靠单一字段兜底 |
| **F. API 语义** | 行为诡异但不报错 | 每个非默认参数都去源码读定义 |
| **G. 版本兼容** | 换客户端即崩 | 特性检测 + 优雅降级 |
| **H. id 冲突** | 技能静默失效 | 技能 id 带扩展专属前缀，不与官方撞名 |

## 四、硬性检查清单（写完必须逐条回答）

1. **技能类型**：锁定技 → `locked: true` **且** `forced: true`；宗族技 → `clanSkill: true`；静默子技能 → `silent`/`charlotte`/`popup: false`。描述里有「可」字才允许询问玩家。
2. **id 唯一**：角色 id 与技能 id 都带扩展前缀；新增技能前先在引擎里 grep 确认不撞名。
3. **时机核实**：`trigger` 里每个时机名，都必须在引擎源码里 grep 到**实际使用处**，不能凭印象。`player` / `target` 两个 role 的语义要想清楚（技能是"我参与"还是"我被指定"）。
4. **API 核实**：用到的每个引擎 API 及其**每一个参数**，都在源码里找到定义并确认语义。
5. **跨表一致**：`characters` / `skills` / `translates`（含 `_info`/`_bg`）/ `characterSort` / 头像文件 / `info.json` 六处互相自洽。
6. **资源生命周期**：写进 `player.storage` 的数据，说明何时清理；`onremove` 里区分「可丢弃」与「必须归还」（牌不在游戏内时需特别注意）。
7. **边界条件**：平局、无手牌、目标非法、牌不足、角色已死亡/已离开，逐个写明行为。
8. **异步**：任何传入的异步回调都要 `await`；`forResult()` 的返回值字段要用对。
9. **不碰未文档化结构**：不依赖引擎未公开的 DOM/内部字段；确需修正引擎行为，用扩展侧幂等补丁并注释原因。
10. **不动游戏本体**：所有改动落在扩展目录内，随 zip 分发即生效。

## 五、可供机器执行的检查（见 `check-extension.mjs`）

能自动化的部分就别靠人眼：

- 语法检查（`node --check`）
- 跨表一致性（角色↔技能↔翻译↔排序↔头像）
- 技能类型字段完整性（锁定技必须同时有 `forced`）
- id 撞名（对照引擎源码 grep）
- `storage` 写入处是否都有对应的 `init`/`onremove`
- 引擎 API 名是否真实存在
