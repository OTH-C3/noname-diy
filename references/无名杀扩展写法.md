> 分两部分：
> - **第一部分：制作途径** —— 有哪几种方式做扩展（官方工具 / 民间做法 / 第三方工具）
> - **第二部分：代码写法** —— 真写起来有几种写法
>

>
> **版本基准**：文中的引擎行号按 **无名杀 v1.11.5.2**（`<游戏目录>/resources/app`）核对过。

# 第一部分 · 制作途径

## A. 官方提供的

### A1. 官方脚手架（仓库内开发）

```bash
pnpm init:extension <扩展名> [--author <作者>] [--vue]
```

- 实现：`scripts/initExtension.ts`，模板在 `scripts/extension-template/{default,vue}`
- 产物目录：`packages/extension/<扩展名>`（该目录只提交 `.gitignore`，**第三方扩展不入官方主树**）
- 模板是 **TypeScript + Vite** 工程：`src/index.ts` + `vite.config.ts` + `package.json`
- **构建产物**才写进 `apps/core/extension/<扩展名>`
- 模板自带 `LICENSE`(GPL-3.0) / `image/` / `audio/`

**适合**：想用 TS 类型提示、要打包压缩、要在 monorepo 里开发的人。
**代价**：得装 Node 工具链，且依赖官方 workspace。

### A2. 游戏内「制作扩展」

选项 → 扩展 → 制作扩展 → 输入扩展名 → 确定。

引擎会生成 `extension.js` + `info.json` + `README.md` 三件套（模板见
`noname/ui/create/menu/pages/exetensionMenu.js:402-424`）。

**适合**：完全不想碰命令行的人。
**代价**：只能在游戏里编辑，功能有限。

### A3. 官方一手文档（写的时候查）

| 文档 | 内容 |
|---|---|
| `docs/lib-skill-format.md` | `lib.skill` 格式速查：触发技 / 主动技 / 视为技 / mod / group / AI 模板 |
| `docs/async-guide.md` | Async Content 写法 |
| `docs/player-event-object-parameters.md` | 对象参数 |
| `docs/skin-guide.md` / `docs/audio-guide.md` | 皮肤 / 配音 |
| `CONTRIBUTING.md` | 官方硬规范（Async Content 强制、对象参数、Tab 缩进、`pnpm lint`） |

**注意**：官方**没有**面向第三方扩展作者的「扩展开发指南」——
最接近的就是上面这几份，其余靠读源码。

## B. 民间做法

### B1. 手写（最普遍）

自己建一个文件夹，写 `extension.js` + `info.json`，放进 `extension/`。

**变体**（都是手写的不同组织方式）：
- 单文件：所有内容都放在 `extension.js`
- 多文件：拆成 `character/character.js`、`card/card.js`、`skill/skill.js`
- 模块化：`src/` 下按职责拆（`data.js` / `translate.js` / `patchAssets.js`），入口只做装配

**适合**：绝大多数个人作者。
**代价**：没有类型检查，全靠自己把关。

### B2. 从别人的扩展改

拿一个能跑的同类扩展当形状基准，改数据与技能。
社区最常见的入门方式，也是本 skill 推荐的起点。

### B3. 扩展模板仓库

社区有人把「联机扩展模板」「武将模板」单独放仓库，直接 clone 改。
（来源多为 QQ 群流传的教程，公开成文的不多。）

## C. 第三方工具

### C1. 打包工具：`@noname-tools/nonametool`

npm 包（MIT），目前**打包口径的事实标准**：

```bash
nonametool pack     # 全量打包成 {prefix}.zip（zip 根目录直接是扩展文件）
nonametool diff     # 基于 git tag 的增量包
nonametool format   # 代码行内规范化
```

配置 `.nonametoolrc`：`zipPrefix` / `exclude` 等；扩展名与版本从 `info.json` 读；
内置排除素材包（`sanguoaudio` / `sanguoskin` 等）与 `node_modules`、`typings`。

### C2. TS 类型提示库

社区有人单独发 `noname-typings` / `noname-ts` 这类类型定义包，
让手写 js 也能有补全。**非官方**，版本可能滞后。

### C3. 网页版工坊

有人做过网页 DIY 工作台（解析 / 编译 / 生成 / 打包）。**本 skill 自带的 `workshop/` 也是这一类。**

### C4. AI 工具

社区有把「写扩展」做成 AI skill 或插件（含校验、读写、素材复制等工具）。
**本 skill 属于这一类**，但走的是「表单 + 对话」而不是「一键生成」。

## D. 分发形态（做完怎么给别人）

| 形态 | 说明 |
|---|---|
| **zip 导入**（主流） | 解压到 `extension/`，或游戏内「获取扩展 → 导入扩展」选 zip；**zip 也能直接拖到游戏窗口** |
| 单独分支放构建产物 | "下载 output 分支直接导入" |
| Release / 仓库内放 zip | 下载即用 |
| **扩展源仓库** | 游戏内「获取扩展」按源拉取（需维护更新索引） |
| **整包重打包** | 连游戏一起打包分发（整包分发） |

## E. 制作途径汇总表

| 途径 | 官方/民间 | 需要工具链 | 适合 |
|---|---|---|---|
| 官方脚手架（TS+Vite） | 官方 | 要（Node + pnpm） | 想要类型检查与构建 |
| 游戏内「制作扩展」 | 官方 | 不要 | 完全不想碰命令行 |
| 手写 js 丢文件夹 | 民间 | 不要 | 绝大多数个人作者 |
| 从别人扩展改 | 民间 | 不要 | 入门 |
| 模板仓库 clone | 民间 | 不要 | 快速起步 |
| nonametool 打包 | 第三方 | 要（Node） | 规范化分发 |
| 类型提示库 | 第三方 | 可选 | 手写时想要补全 |
| 网页工坊 / AI 工具 | 第三方 | 不要 | 不想写代码 |

# 第二部分 · 代码写法

> 以下是真写起来时的可选写法。**列在表里的都合法**，没有哪个是错的。



> **这份文档只做列举，不做筛选。**
> 凡是引擎支持、或社区实际在用的写法都列出来，并标注出处与占比。
>
> 如果你要判断"我该用哪种"，看每节末尾的「怎么选」；
> 但**列在表里的都是合法写法**，没有哪个是错的。

## 一、扩展入口：两种，各占一半

出处：`noname/init/import.js:64-68` —— 引擎的判定逻辑是：

```js
if (!modeContent.type) return;                        // 没有 type → 静默跳过
if (modeContent.type !== type) throw new Error(...);  // 有 type 但不匹配 → 报错
await game.import(type, modeContent.default);
```

**这解释了两件事**：
- 有 `type` 且值正确 → 引擎按 ESM 方式注册
- **没有 `type`** → 引擎**跳过**，转而靠模块顶层的 `game.import(...)` 副作用生效

### 写法 1：ESM 导出

```js
import { lib, game, ui, get, ai, _status } from "../../noname.js";
import { packs } from "./character/character.js";

export const type = "extension";

export default function () {
	return {
		name: "扩展名",
		/* ... */
	};
}
```

### 写法 2：`game.import`

```js
import { lib, game, ui, get, ai, _status } from "../../noname.js";

game.import("extension", function () {
	return {
		name: "扩展名",
		/* ... */
	};
});
```

**实测占比**（统计的 14 个扩展里，带 `extension.js` 的）：**两种各 5 个**。

**怎么选**：写法 1 能被工具静态看出类型，推荐新扩展用；写法 2 是老写法，照样能跑。

## 二、包类型：引擎支持 5 种

引擎里注册过的包类型（`game.import("<类型>", ...)`）：

| 类型 | 挂载到 | 引擎侧出现次数 | 干什么 |
|---|---|---|---|
| `character` | `lib.characterPack` | 18 | 武将包 |
| `extension` | `lib.extensionPack` | 5 | 扩展本体 |
| `mode` | `lib.modePack` | 4 | 玩法模式 |
| `play` | 玩法列表 | 社区 3 次 | 老式玩法包（`boss` / `cardpile` / `coin` 用这个） |
| `card` | `lib.cardPack` | 见下 | 卡牌包 |

**`card` 说明**：`lib.cardPack` 在 `noname/library/index.js:124` 有定义，
说明引擎支持；但实际见过的扩展里没有单独用它注册的 —— 社区的卡牌通常跟着
`character` 包的 `card` 字段一起给。

**怎么选**：加武将用 `character`；加卡牌可以单独注册 `card`，也可以塞进 `character` 包的 `card` 字段。

## 三、包内容怎么组织：三种

### 方式 1：顶层 const + `packs`（社区主流）

```js
const characters = { /* ... */ };
const skills = { /* ... */ };
const translates = { /* ... */ };
const characterTitles = { /* ... */ };
const characterSort = { /* ... */ };
const characterSortTranslate = { /* ... */ };

export const packs = {
	character: {
		connect: true,
		character: characters,
		characterSort,
		characterTitle: characterTitles,
		translate: { ...translates, ...characterSortTranslate },
	},
	skill: { skill: skills, translate: translates },
};
```

然后在入口里 `package: { ...packs, author, intro, version }`。

### 方式 2：直接内联进 `package`

```js
export default function () {
	return {
		name: "扩展名",
		package: {
			character: { character: {...}, translate: {...}, characterTitle: {...} },
			skill: { skill: {...}, translate: {...} },
			card: { card: {...}, translate: {...}, list: [] },
		},
	};
}
```

**官方脚手架生成的模板就是这种结构**（`scripts/extension-template/default/src/index.ts`）。

### 方式 3：`game.import` 独立注册包

```js
export const type = "extension";
export default function () {
	return {
		name: "扩展名",
		content() {
			game.import("character", function () {
				return {
					name: "包名",
					character: {...},
					skill: {...},
					translate: {...},
					characterTitle: {...},
					characterSort: { 包名: {...} },
				};
			});
		},
	};
}
```

**注意**：这种写法的 `characterSort` 第一层 key 是**包名**，可以**不等于扩展名**。

**怎么选**：方式 1 最清晰；方式 2 是官方脚手架的做法；方式 3 适合"一个扩展里塞多个独立包"。

## 四、角色定义：两种

### 对象式

```js
const characters = {
	角色id: {
		sex: "male",
		group: "wei",
		hp: 3,
		skills: ["技能id1", "技能id2"],
	},
};
```

### 数组式

```js
const characters = {
	角色id: [性别, 势力, 体力, [技能id...], [附加项...]],
	// 实例：['female', 'shen', 3, ['zqzaoren', 'zqbutian'], ['gzgroup:ye']]
};
```

**两种引擎都认**（`noname/init/loading.js:234-282` 分别处理）。

**怎么选**：对象式可读性好；数组式紧凑，内置包与超多武将的扩展常用。

## 五、翻译表：三种写法

| 写法 | 说明 |
|---|---|
| `const translates = {...}` + `export const packs` 里引用 | 社区主流 |
| `const translate = {...}`（单数名） | 引擎两种名字都认 |
| 直接内联进 `package.character.translate` | 官方脚手架模板 |

**另外**：**同一张表可以分几段写**（例如入口附近一段、角色定义旁一段），
引擎会合并 —— 但**文本解析工具会漏掉后面的段**，所以工具要按"多段合并"处理。

**表里的键**（都是可选的，缺了会有相应后果）：

| 键 | 用途 | 缺了会怎样 |
|---|---|---|
| `<角色id>` | 武将显示名 | 界面显示英文 id |
| `<角色id>_ab` | 简称 | 用全名 |
| `<角色id>_prefix` | 称号的另一种写法 | 用 `characterTitle` |
| `<技能id>` | 技能名 | 显示英文 id |
| `<技能id>_info` | 技能描述 | 技能详情空白 |
| `<技能id>_bg` | 标记显示字 | 取技能名首字 |
| `<gaintag>` | 牌面标记文字 | 牌上显示英文 id |

## 六、技能定义：两种

### 完整对象

```js
const skills = {
	技能id: {
		trigger: { player: "damageAfter" },
		forced: true,
		locked: true,
		async content(event, trigger, player) { /* ... */ },
	},
};
```

### 子技能内联（`subSkill`）

```js
const skills = {
	技能id: {
		trigger: {...},
		content(...) {...},
		group: ["技能id_子技能"],
		subSkill: {
			子技能: { /* 独立定义，自动展开为 技能id_子技能 并补 sub/sourceSkill */ },
		},
	},
};
```

引擎会在展开时补 `sub: true` 与 `sourceSkill`（`noname/game/index.js:8761-8782`）。

## 七、`info.json`：字段

```json
{
	"name": "扩展名",
	"intro": "简介",
	"author": "作者",
	"diskURL": "",
	"forumURL": "",
	"version": "1.0"
}
```

- **不是必需的** —— 缺了引擎用兜底值（作者显示"未知"，`noname/init/import.js:85-98`）
- 社区还出现过两个非官方字段：`minNonameVersion`、`importConfig`，**由扩展自己或启动器读取，引擎不解析**

## 八、目录布局：两种

### 扁平（小扩展）

```
扩展名/
├── extension.js
├── info.json
├── README.md
├── 角色id.jpg
└── character/character.js
```

### 分类（大扩展）

```
扩展名/
├── extension.js
├── info.json
├── image/character/角色id.jpg
├── audio/die/角色id.mp3
├── audio/skill/...
└── character/character.js
```

**立绘的默认规则**：引擎**只在扩展根目录**找 `<角色id>.jpg`
（`noname/init/loading.js:257-262`）。
**放子目录必须显式写 `img`** —— 社区扩展没写 `img` 却放子目录的情况很常见，
工具读的时候应该多探几个常见位置（根目录 / `character/` / `character/characters/` / `image/` / `image/character/`）。

## 九、汇总表：写法的所有组合

| 维度 | 可选值 | 出处 |
|---|---|---|
| **扩展入口** | ESM 导出 / `game.import` | 引擎判定逻辑 + 实测各半 |
| **包类型** | `character` / `card` / `mode` / `extension` / `play` | 引擎注册记录 |
| **包组织** | 顶层 const + packs / 内联 package / `game.import` 独立注册 | 社区实例 + 官方模板 |
| **角色定义** | 对象式 / 数组式 | 引擎两条处理分支 |
| **翻译表** | `translate` / `translates` / 内联；可分段 | 引擎两种名字都认 |
| **技能定义** | 完整对象 / `subSkill` 内联展开 | 引擎展开逻辑 |
| **info.json** | 六个字段；可缺 | 兜底逻辑 |
| **目录布局** | 扁平 / 分类（分类需显式 img） | 引擎默认路径规则 |

## 十、工坊（读扩展）能覆盖到哪

| 写法 | 能自动读 |
|---|---|
| ESM 入口 + 对象式 + 顶层 const | 能 |
| ESM 入口 + 数组式 + 顶层 const | 能 |
| 内联 package | 能（部分） |
| `game.import` 入口（扩展） | 能（读里面的顶层 const） |
| `game.import` 独立注册包 | **不能** → 提示手填 |
| 动态生成（版本条件、循环拼接） | **不能** → 提示手填 |

**读不出时**：不猜、不填半截，明确提示「这个扩展的结构读不出来，请手动填」。

---

## 十一、给扩展作者的建议（可选，不是规定）

如果希望工具能读懂你的包：

1. 入口用 ESM（`export const type`）
2. 角色用对象式
3. 字段放顶层 `const`，再在 `packs` 里组装
4. 翻译表叫 `translates` 或 `translate`，**尽量不要分太多段**
5. 立绘放根目录，或写了 `img` 再放子目录

**不做这五条也能跑** —— 只是自动工具读起来会吃力，需要手填。
