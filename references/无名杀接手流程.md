# 无名杀接手流程

> 用户在网页工坊提交后，会在对话里说一句「我提交了」。
> **这份文档规定接下来该怎么做** —— 每次照这个来，不要自由发挥。
>
> `SKILL.md` 里只放要点，完整流程在这里。
>
> **开口之前先做「阶段 0」**（查电脑齐不齐），再进场景 A / B。

---

## 阶段 0 · 查环境（每次开工先做，一个会话一次）

缺少依赖不是用户的错，但继续执行只会让他看到报错。

**先看一眼有没有待识别的卡面**：`<工作区>/.diy-workshop/card-source.json` 存在、
且 `card-import.json` 还没写 → 说明用户在工坊上传了图、点过「识别卡面」，正等结果。
**这时不用等他专门说「识别卡面」** —— 他随便说句什么都行，你直接按 `卡面识别.md` 的流程读图识别。
做完把 `card-import.json` 写上，前端几秒内会自动填表。

| 要什么 | 怎么查 | 用途 |
|---|---|---|
| Node.js | `node -v` | 开工坊网页、自动检查代码 |
| Python 3 | Linux / macOS：`python3 --version`；Windows：先 `python --version`，不行再 `py --version` | 打包成游戏能装的压缩包 |
| **无名杀** | 见下节（**不在 PATH 里，只能找目录**） | 对照检查 API 名、id 撞名 |

**打印出版本号 = 有**；「不是内部或外部命令」/「command not found」= 没有。

### 找无名杀

**优先问用户要路径，其次自行检索**（问「装在哪个文件夹」，不要说「安装目录」）。
**无需下载源码包** —— 游戏安装目录内含完整引擎源码（Electron 客户端为 `resources/app/`）。
**skill 本身不含源码**，只含文档；引擎源码只能来自用户已装的游戏，或线上仓库。

```bash
find ~ -maxdepth 4 -type d -iname "*无名杀*" 2>/dev/null
find ~ -maxdepth 4 -type d -iname "*noname*" 2>/dev/null
find ~ -maxdepth 6 -type f -name "noname.js" 2>/dev/null
```

常见位置：Windows `D:\`、桌面、`下载`；Linux / macOS `~/下载`、`~/Desktop`、`~`。

**识别判据**：目录内同时存在 `character/`、`game/`、`noname/` 与 `noname.js`。
Electron 客户端（懒人包）为 `<安装目录>/resources/app/` —— 该目录即引擎源码根。

定位后作为第二参数传入：

```bash
node <skill目录>/scripts/check-extension.mjs <扩展目录> "<引擎源码根>"
```

（省略亦可：脚本逐级向上检索「引擎源码」目录；未命中则跳过三项依赖它的检查。）

**未找到 / 未安装时降级继续，不阻塞**：仅缺三项自动校验（时机名、id 冲突、引擎 API 存在性），
改用 `references/` 字段表人工核对。无需为此安装完整游戏 —— 用户要进游戏验证时会自行安装。

### 缺失处理

- **禁止**：改系统配置、以其他工具顶替、猜测命令硬跑、虚构可运行状态
- **要求**：停止推进，向用户说明「缺什么、去哪装、装好告知」

| 缺什么 | 照这句话说就行 |
|---|---|
| Python | 「你电脑上还差一个 Python，装完我才能把武将打包成游戏能装的压缩包。去 python.org/downloads 下载，装的时候一路点下一步 —— Windows 记得勾上『Add python.exe to PATH』。装好回来说一声，我们接着做。」 |
| Node.js | 「还差一个 Node.js（用来开那个填表的网页、自动检查代码）。去 nodejs.org 下载 LTS 版，一路点下一步装完就行。装好回来说一声。」 |
| 无名杀 | 「你电脑上装了无名杀吗？装了的话告诉我它在哪个文件夹，我对着它核对一下技能里的写法。**没装也行** —— 那就先做，只是少一道自动检查，等你真要玩的时候再装。」 |

> 前两样缺了要**停下等用户装**（不然走到一半会卡住）；**无名杀不影响开工**，
> 问一句、找不到就往下做，别为它耽误。

装完**再查一次**确认，然后接着往下走。

### 频率与降级

- 每会话查一次，不必逐轮
- 缺 Node.js：仍可写武将，仅工坊与静态检查不可用
- 缺 Python：打包阶段阻塞 —— 提前告知，勿等最后
- 用户称「不懂这些」：原样转发上述话术，不加术语

### 环境就绪后启动工坊

**主动启动并告知 URL**（默认入口，不等用户问）：

```bash
node <skill目录>/workshop/server/server.mjs
# 打印实际 URL，默认 http://127.0.0.1:8765/
```

- 已在运行则不重复启动（先探 `/api/health`）
- **以终端输出为准**：默认端口占用时自动递增
- 用户选择纯对话模式 → 跳过工坊，走场景 B，不劝其使用网页

## 场景 A：用户用过网页工坊，说「我提交了」

最常见的入口。**按四阶段走，不要跳步。**

### 阶段 1 · 接手（读 + 校验）

| 步 | 做什么 | 缺失时怎么办 |
|---|---|---|
| 1 | 读 `<工作区>/.diy-workshop/latest-request.json` | 读不到就问用户「提交成功了吗」 |
| 2 | **看时间戳 `submittedAt` 与 `processed`** | 隔了几天就确认「这份还是最新的吗」，不要以旧需求为准；`processed: true` 说明**已经处理过**，先问用户是不是又提交了一次，别重复干活 |
| 2.5 | **处理完把 `processed` 改回 `true`**（直接改那个 JSON） | 不改的话下次接手分不清这份做没做 —— 这只花一秒钟 |
| 3 | **校验必填**：扩展名 / 武将名 / 至少一个技能 | 缺就问，别自己补 |
| 4 | **查重**：`<工作区>/扩展源码/<扩展名>` 与游戏包 `resources/app/extension/<扩展名>` | 已存在且 `extMode` 是新建 → **停下来问**：追加武将还是换名字 |
| 5 | **看立绘** `avatarPath` 指向的文件 | 不在就说「立绘丢了，可重新提交或不用立绘」 |

**体力字段 `hp` 怎么读**：网页里填的是「体力/上限/护甲」三段，例如 `4/6/2`
= 体力 4、上限 6、护甲 2；护甲为 0 也照写（`4/4/0`）。这正是游戏本身的写法
（`references/无名杀武将指南.md` 2.3），实现时直接用：写成 `hp: "4/6/2"`。
全部相同且护甲为 0 时，可以简写成数字 `hp: 4`。
网页那边已经保证体力不会大于上限（超了就自动把上限抬上去、填平），只收数字与 `/`。

**势力字段 `group` / `groupCustom` 怎么读**：`groupCustom` 非空时**以它为准** —— 这时
`group` 是空串（工坊故意留空，免得照内置值写错）。自定义势力必须按
`references/无名杀规范.md` 7.4 在 `content` 里生成 `game.addGroup(...)` 注册，
不能裸写字符串（否则丢配色、丢国战与势力数语义）。`groupCustom` 为空时，
`group` 是内置六势力之一，直接用。

**台词字段 `skills[].lines` 怎么读**：网页里的技能台词框是**一行一句**，
读进来就是字符串数组（空行与首尾空白网页侧已经去掉；一句都没填时**不带这个键**）。

- `skills[].lines` → 该技能的台词：第 n 句写进 `translate` 的 `"#<技能id>n"`

落笔的细节（键要加引号、不带文件后缀、序号从 1 起且要连续）见
`references/无名杀规范.md` 8.1。**台词不出字幕**，只在**武将详情页**里显示 ——
用户若以为「发动技能时会弹字幕」，先照 8.1 的出处说明白，别顺着他的预期含糊过去。
用户还想真出声，得自己把 mp3 放进扩展的 `audio/` 里、并给技能写上 `audio` 字段
（路径规则见同一份规范的「十六、素材路径」）。

**阵亡台词**（2026-10-10 晚起工坊收了，在第四步「更多拓展」里）：payload 的
`dieLines` 是一行一句的数组。落盘时键是 `"#<角色id>n:die"`（n 从 1 起），并且
**角色定义里必须写 `dieAudios: <句数>`** —— 写 `true` 引擎只会读第 1 句
（`get/audio.ts:226-229`，数字式才按下标逐条取）。

**国战归属与多势力**（2026-10-10 晚起工坊收了，同在第四步「其四」）：
`guozhanGroup`（单值）与 `doubleGroups`（数组）只可能是魏蜀吴群晋，写进角色定义的
`groupInGuozhan` / `doubleGroup`。三件事别漏：

- 值必须在 `lib.group` 里，否则引擎转换 tag 时**静默丢弃**（`element/character.js:365`）
  —— 自定义势力要先按规范 7.4 注册；
- **packs 的 character 组里要加 `mode: "guozhan"`**，否则整个扩展进不了国战卡池
  （`init/loading.js:279`）；
- 两个键空着就不带 —— 不要清除用户已写的国战字段。写法详见规范 7.5。

**扩展包介绍 `intro` 怎么用**：这是**整包**级字段，写进那个扩展的 `info.json`，
不是某个武将的内容。规则只有两条，但第二条必须守住：

- payload 里**有** `intro` → 写进 `info.json` 的 `intro`（新建时一并创建；
  「加入已有 / 修改已有」时改写**那个扩展**的）。字段含义与 HTML 注意事项见规范 11.1。
- payload 里**没有** `intro` → **一个字节都别动那个 `info.json` 的 `intro`**。
  空值刻意不带这个键，防的就是这个：「加入已有」时用户没填介绍，
  绝不能把人家扩展原有的简介清掉。

它**不属于任何一个武将** —— 别写进 `translate`，也别塞进角色条目。

**资料页字段 + 选将包名**（2026-10-10 深夜起工坊收了，在「扩展包介绍」下面；
**2026-10-11 下午：网盘/论坛链接撤了** —— info.json 六字段仍支持，用户想要在对话里说）：
`author` / `version` 与 intro 同一套规矩 —— payload 里有才写
（新建时写进 `package` 与 `info.json`；「加入已有 / 修改已有」时只动 payload 里出现的键）。
`packDisplayName` 的落法不同：写进 **packs 的 character 组 translate 里、key 为扩展名**的条目 ——
引擎看到 `translate[扩展名]` 会把它写成选将界面的包名
（`init/loading.js:198-200`：`translate` 的这个 key 直接变成 `<扩展名>_character_config`）：

```js
character: {
	connect: true,
	character: { /* ... */ },
	characterSort: { /* ... */ },
	translate: {
		"我的扩展": "自定义包名",   // ← 选将界面里就显示这个
	},
},
```

这个条目默认可以不写（引擎兜底显示扩展名）；**「加入已有」时注意不要删掉其中已写好的条目** ——
payload 没带 `packDisplayName` 就原样保留原文件里那个条目。

**技能类型勾选**（2026-10-11 起：第四步每个技能块上的一排勾，**自动跟着描述关键词勾**，
用户可手动改）：`skills[].types` 是数组，取值仅限
`locked` / `limited` / `juexingji` / `zhuanhuanji` / `zhuSkill` / `clanSkill`。
映射规则（详见规范 5.2 与 7.6）：

- `locked` → 技能上写 `locked: true` **和** `forced: true`（漏写 forced 是真实发生过的问题）；
- `limited` → 只写 `limited: true`，引擎自动补标记 / 介绍 / 动画；
- `juexingji` / `zhuanhuanji` → 标签字段照写，**效果与状态机仍要按描述写代码**；
- `zhuSkill` → 技能上写 `zhuSkill: true`（主公（身份局主公位）才生效）；
- `dutySkill` → 使命技标签 + 标准结构：父技能（`init` 记 storage）+ `subSkill` 里的
  `success` / `fail` 两个子技能（成败触发各自写，成功用 `player.awakenSkill` 收尾，
  官方样例 `src/character/key/skill.js:3999` 的有生之护）；
- `clanSkill` → 同下条宗族，且要求角色写 `clans`。

**宗族与宗族技**（2026-10-11 起工坊收了，第四步「其五 宗族」+ 类型勾选里的「宗族技」）：
`payload.clans`（数组）写进角色定义的 `clans`；类型勾选含 `clanSkill` 时技能定义写
`clanSkill: true`。三件事：

- 宗族技标签本身免费（`get/index.js:821`），但**同宗共享的效果要自己写**：
  `trigger` 用 `global` 监听全场，filter 里判断目标角色的 `clans` 数组含不含我的宗族名
  （官方样例 `src/character/clan/skill.js:1203` 的族泽）；
- 标了 `clanSkill` 却没有任何角色写 `clans` 会被检查脚本报错；
- 描述里提到「宗族」却没标 `clanSkill: true` 会吃警告（检查脚本第 3 类）——
  写描述时「宗族」二字不是闲笔。

**武将列传**（2026-10-11 起工坊收了，第四步「其六 武将列传」）：
`payload.characterIntro`（一段文本，限 1000 字）→ 写进
`lib.characterIntro["<武将id>"]`。落笔二选一：packs 带
`characterIntro: { "<武将id>": "列传" }` 且 `content()` 里
`Object.assign(lib.characterIntro, pack.characterIntro)`；或 content 里直接赋值。
支持 HTML（详情页富文本渲染）。**payload 留空 ≠ 不写** —— 用户可能在对话里让
AI 代写（按史实编几百字），写好后同样落到这个键。详见规范 7.8。

**技能补充说明**（2026-10-11 起工坊收，第四步每个技能块上的「补充说明」多行框；
**2026-10-11 下午起由「动态描述」升级为通用口径**）：`skills[].notes` 是用户对
**效果细节的补充** —— 一切写不进技能描述正文的都在这：使命成败与奖惩、觉醒条件与
觉醒后所得、转换技阴阳两态、**技能变身时机**（路线 B 皮肤在什么时机换）、
动态显示（已生效分支划掉）、数值细节等，通常一行一条
「状态 / 条件 → 结果」。**不是代码** —— AI 据此落到对应机制：

- 动态显示类 → 按规范 7.9 写 `dynamicTranslate`（三纪律：只改显示不改逻辑、幂等、样式走引擎类）；
- 使命技 → 按父技能 + success/fail 子技能结构写（见类型勾选段）；
- 觉醒/转换/数值 → 按描述写进效果本体。

没带 `notes` 的技能不额外发挥。

**皮肤与路线 B 变身**（第四步「其三 皮肤与多形态」）：payload `skins` 每项
`{name, path, tempname?}` —— `name` 是形态名（= 图片文件名 = 路线 A 手选时的显示名），
`path` 是已落盘的图。**带了 `tempname`（变身名）＝这个皮肤要走路线 B**，AI 落盘三件套：

1. `content()` 里写 `lib.characterSubstitute["<角色id>"] = [["<皮肤id>", ["ext:<扩展名>/skin/<角色id>/<形态名>.jpg"]]]`
   （`library/element/player.js:3694-3698` 背书；图片就是 place-assets 归位的那张，不重复放）；
2. packs 的 translate 里加 `<皮肤id>: "<变身名>"` —— 变身时玩家牌上显示的就是它
   （`tempname` 读 translate，皮肤 id 由你按 7.2 前缀规则生成）；
3. 技能里调 `player.changeSkin(map, "<皮肤id>")` —— **变身时机从该技能的
   `notes`（补充说明）里读**（第四步那一栏专门收这个）；`notes` 里没写，
   才在对话里弹窗问（使命成功？转换技阴？回合开始？）。

只做路线 A（手选皮肤）时上面三件都不用写，`skinPath` 一行就够（见规范 7.5/7.7）。

**联机怎么玩自己的扩展**（用户常问，2026-10-11 补）：

- 工坊产出的扩展写死 `connect: true` —— 这就是「联机开关」**开着**的意思：
  联机模式下引擎会完整加载这个包的技能（`init/loading.js:194,202`）。
  **关了反而是废掉**：false 时引擎把技能换成 nopop 空壳，角色在但技能不能用。不要让用户关掉它。
- 联机的游戏逻辑在**服务器**跑：用户想和朋友玩自己的扩展，
  **承载房间的那一方必须装这个扩展**（官方/第三方联机平台建房时可携带；
  自己开服就是自己装）。
- 其他玩家**建议也装**同一个扩展 zip（扩展管理导入并启用）：不装不影响游戏运行
  （逻辑不缺），但他那边**看不到立绘、名字显示英文 id、技能描述空白** —— 渲染是各客户端本地的。
- 提醒用户：数值型、简单选择型的技能联机没问题；重度依赖动画 / 本地 UI 的复杂技能
  在联机里可能表现与单机不同 —— 这类情况让他先试一局。

**配音文件 `skills[].audioFiles` 怎么用**：用户在工坊里给技能配了 mp3，
服务端**已经落到** `<工作区>/.diy-workshop/audio/` 下，payload 给的是绝对路径，
**第 n 个 = 第 n 句台词**。打包时照做：

1. **复制并改名**进扩展目录的 `audio/`：第 n 个文件 → `<技能id>n.mp3`
   （技能 id 用你生成的英文/拼音，**不能用用户填的中文技能名**）
2. 技能上写 `audio: "ext:<扩展名>/audio:<文件数>"` —— 「路径 + 数字」之间是 `:` 不是 `/`
3. 句数要对上：配音 2 个文件、台词却写了 3 句，就对不齐了 —— 这种情况先问用户

**没有 `audioFiles` 就是没配音**：这时**别写 `audio` 字段**，但台词键照写
（`translate` 的 `"#<技能id>n"`）—— 介绍页里有字、不出声，这是正常状态，不用提醒用户"缺配音"。

「修改已有」**不回填配音**（工坊不从已有扩展的 `audio/` 读文件）——
用户要换配音，重新选择文件即可。文件名与 `audio` 的对应关系见规范 8.1。

#### 情况 B：「修改已有」提交（`extMode` 为 `edit`）

payload 里会多一个 `editTarget`：

```json
"editTarget": {
  "extName": "测试",
  "characterId": "cs_guotu",
  "source": "installed",
  "original": { "name": "郭图", "title": "妄画蛇足", "hp": 3, "skills": [...] }
}
```

**处理要点（顺序照做）**：

1. **先算改动**：把 payload 里的 `name` / `title` / `group` / `sex` / `hp` / `skills`（含
   `skills[].lines`）与 `original` **逐字段比对**，列出**真正变了的字段**。
   `intro` 不跟 `original` 比 —— 它是整包级的，要和那个扩展**现存的 `info.json`** 比。
   汇报时把这个对比列出来，让用户一眼看到「你改了哪几处」。
   **比体力时按等价算**：表单是 `3/3/0`、原文件是 `hp: 3`（或 `4/6/0` 对 `{hp:4, maxHp:6}`、
   `4/6/2` 对 `hp:"4/6/2"`）都算**没改** —— 表示法不同不等于用户动了设定。
2. **确认落点**：
   - `source: "installed"` → 在工作区或游戏包里找到那个扩展
   - `source: "upload"` → 落点就是 payload 里的 **`uploadPath`**
     （`<工作区>/.diy-workshop/uploaded/<扩展名>/`）—— 服务端解析后会**在工作区保留一份**，
     直接在那个目录里改。
     **只有当 `uploadPath` 缺失、或那个目录已经不在了**（用户清过 `.diy-workshop/`），
     才需要让他重新上传，或从游戏包里找同一份扩展。
3. **改翻译表，不改技能代码**：

   | 用户改了什么 | 落到哪 |
   |---|---|
   | 技能名 | `translate` 里 `[技能id]` |
   | 技能描述 | `translate` 里 `[技能id + "_info"]` |
   | 技能台词 | `translate` 里 `"#<技能id>n"`（第 n 句） |
   | 武将名 | `translate` 里 `[角色id]` |
   | 称号 | `characterTitle` / `characterTitles` 里 `[角色id]` |
   | 势力 / 性别 / 体力 | 角色定义里的 `group` / `sex` / `hp` |
   | 扩展包介绍 | **同目录的 `info.json` 的 `intro`** —— 注意它**不在**角色定义里，是整包级的 |

   **技能的实现代码不动** —— 用户要改效果，那是另一件事，走新建或明说。

   **台词改少了要把旧键一起删掉**：留着 `"#<技能id>3"` 这种已经没有对应台词的空位，
   介绍页仍会把上一版的台词列出来。改完一并核对这个技能的 `#` 键，序号是否还连着。
4. **改前备份**：先把原文件复制一份 `<文件名>.bak`。
5. **改后回读**：确认改动真的落盘，且**同一文件里其他武将没被牵连**。
6. **汇报时给出**：改了哪个文件的哪几行、备份路径、其他武将未受影响。

**绝不做的事**：整块重写整个 `character.js` —— 那会丢掉文件里别的武将、
注释、以及用户自己写的特殊写法。

#### 情况 C：来源是官方包（payload 带 `officialTemplate`）

用户在「选择扩展包」里点了**官方包**，挑了一个官方武将当模板：

```json
"officialTemplate": {
  "pack": "bingshi",
  "packLabel": "兵势篇·奇 / 兵势篇·正",
  "characterId": "pot_heqi",
  "characterName": "势贺齐"
}
```

**红线（先看这段）**：

- **官方武将不能改** —— 游戏本体是只读的。绝不往 `<游戏>/resources/app/character/`
  或 `<游戏>/resources/app/extension/` 里写任何文件。
- 产物一律是**新建的独立扩展**：`<工作区>/扩展源码/<用户填的扩展名>/`。
  表单里那个扩展名就是新扩展名（选了官方包之后它是空的，等用户填）。
- 这种 payload **没有 `editTarget`、也没有 `uploadPath`** —— 则不得就地修改任何内容。

**几条要留意的**：

- 读出来的技能描述已经清过官方包的**运行时插值**（`${get.poptip({...})}` 这类，
  文本解析拿不到求值结果，原样给用户看就是一坨代码）。那是**模板文本**，不是用户的原话；
  用户到底要什么，以表单里他改过的描述为准。
- 官方武将的**立绘**是从 `<游戏>/image/character/<角色id>.jpg` 取出来的**参考图**，
  已经复制到工作区并送进裁剪器。**不进产物** —— 除非用户自己裁了/传了立绘。
- 要写技能实现时，**同名技能的官方实现就在同一个包文件里**
  （`<游戏>/resources/app/character/<pack>.js`），可以先看它怎么写的
  —— 但只作参考，不要直接搬运官方实现（含它引用的运行时插值）。
- 官方包里有大量**非武将**内容（卡牌、拼音表、国战配对、语音表…）。
  工坊只列"能读出武将"的包，读的时候也只取角色/技能/翻译/称号那几张表。

#### 上传过的包：`uploadPath`

`extMode` 是 `existing`（加入已有）或 `edit`（修改已有）、而且用户是**上传 zip** 的时候，
payload 里会多一个 `uploadPath`：那是服务端解压后**保留在工作区**里的扩展目录
（`<工作区>/.diy-workshop/uploaded/<扩展名>/`）。用法：

- `existing` → 把新武将**追加**进这个目录的 `character/character.js`，
  不新建扩展、也不改动里面已有的武将
- `edit` → 就在这个目录里改字段（`source` 仍是 `upload`，但这次改得回文件了）

没有 `uploadPath` 时，按 `extName` 去工作区「扩展源码」或游戏包里找那个扩展。

### 阶段 2 · 理解（复述 → 审查 → 问歧义）

#### 2.1 先复述一遍（快、短）

**读完 JSON 后立刻用自己的话把技能复述一遍** —— 不是照搬原文，是讲**你理解的效果**：

> 我理解一下：
> - 「诋訾」——你受伤后可以把某个角色的一张牌放到他武将牌上，称为"诋"；
>   期间他使用了同类型的牌，就得在"掉 1 血"和"再塞一张牌进去"里选一个。
> - 「戌嗥」——出牌阶段，你可以卜算并视为使用一张基本牌或普通锦囊；
>   造成伤害就重铸所有"诋"，没造成就自己掉 1 血。

**复述的作用**：

- 用户立即发现理解偏差
- 偏差此时修正，成本远低于写完后返工
- 不构成「伪阻断」（非求确认，是给用户打断的机会）

#### 2.2 对比，觉得离谱就直说

复述的同时**审一遍合理性**。凡是让你觉得**离谱、矛盾、与规则冲突**的，**直接讲出来**：

| 类型 | 例子 | 怎么说 |
|---|---|---|
| **数值离谱** | "X 为全场牌数" | "这个 X 轻轻松松到几十，强度会失真 —— 建议加上限或换口径" |
| **逻辑矛盾** | "锁定技，你可以选择…" | "锁定技不能带'可以选择'。这里要删'可以'，还是改成非锁定？" |
| **与规则冲突** | "受到的伤害减半" | "伤害在引擎里是整数，减半得定清向上还是向下取整" |
| **时机不可能** | "回合外使用【杀】" | "回合外一般用不了【杀】，除非有特殊许可 —— 这条要确认" |
| **无意义条款** | "若你没有手牌，则视为你有手牌" | "这句等于什么都没做，是不是写错了？" |
| **会死循环** | "造成伤害后，再次发动本技能" | "这会无限触发，得加'每回合限一次'" |
| **前后重复** | 两个技能干了同一件事 | "这两条效果重叠了，是有意的还是笔误？" |

**上面这张只是入门。完整版按六类展开、每类都给了「症状 → 后果 → 怎么问」** →
`references/无名杀设计审查清单.md`。里面另有两块这张表没有的：

- **第五类「会让引擎卡死」**（死循环、自我触发、filter 里有副作用、`onremove` 让牌永久消失）
  —— 这类**不用问用户**，直接按正确写法做
- **第六类「最容易被想当然补错的」**（擅自加 `usable`、擅自加 filter 前置条件、收紧牌型）
  —— 这类是 AI 自己加戏，不是描述的问题

**什么情况必须查规则集**：文档末尾有速查表。判断口诀是
**「这张牌怎么算」查 `规则集要点.md`，「这个技能怎么写」查 `技能系统.md`**。

**表达**：直接、给理由、给替代方案。不因"礼貌"咽下问题 —— 需求里的易错点不指出，最终由用户承担。

**但不对抗**：用户**明确的设计意图**照做（哪怕刻意偏弱/偏强），
仅在**明显笔误或规则上不可实现**时才提。

**再说三遍，这条最容易犯**：

> **技能名与描述原文一字不改。**
>
> 发现有错别字、标点不规范、措辞不通顺 —— **指出来，让用户改**。
> **不许擅自「改通顺」**，也不许改完只在汇报里轻描淡写提一句。
> 描述是用户的作品；你写的是**代码**，不是他的文案。

#### 2.3 然后标歧义，一次性问完

**逐条读技能描述，标出这些点**：

- 触发时机（什么时候发动）
- 频率（每回合几次 / 是否锁定技）
  - 注意：**锁定技必须同时有 `locked` 与 `forced`**
- 目标（谁 / 几张 / 从哪选）
- 数值与边界（X 怎么算、为 0 时怎么办）
- 与已有规则的关系（涉及拼点、距离、结算顺序时，查 `无名杀规则集要点.md`）

**常见歧义速查（下面每一条都是被作者纠正过的）**：

| 描述里的说法 | 容易理解成 | 实际应理解为 |
|---|---|---|
| **每回合**使用前四张牌 | 我自己的回合 | **任何角色的回合**都算 → 重置要用 `{ global: "phaseBegin" }` |
| 弃置**中央区花色数**张牌 | 弃中央区里的牌 | 弃**自己的**牌，张数 = 本回合弃牌堆里的**花色种类数** |
| **无限制地**使用一张牌 | 挂个 buff 撑到回合结束 | **紧接着当场**用一张；"无限"= 无次数限制 + 无距离限制 |
| 然后**使用**一张牌（没有"可以"） | 给一个可取消的询问 | **强制**，不能取消 |
| **任意张**牌 | 想弃几张弃几张（含 0） | 通常至少 1 张；"任意"≠"无限"，范围按描述所指 |
| **可以**弃一张牌 | 也可以不弃 | 可取消 ✓（这是对的）—— 反过来，没写"可以"的一律当强制 |

**分级处理**：

| 级别 | 处理 |
|---|---|
| **影响核心逻辑的歧义** | **用弹窗一次性问完**，别挤牙膏 |
| **有合理默认的** | 自己定，但**写进汇报的「默认裁决」**里 |

**不要重复确认**：歧义问过一次就够了，不要再问「我理解的是不是这样？」
—— 用户说「已提交」是让你动手，不是让你复述。

### 阶段 3 · 实现

1. **定形状基准**：在用户装过的扩展里挑一个同类且能跑的，按它的结构写。

   **基准只解决「形状」** —— 下面四样属于形状：看一个能跑的实现比读文字快。
   **「要件与语义」照旧查 `references/`**（字段含义、时机名、API 签名、规则判定、
   官方技能效果）：那才是主力依据，文档里标了出处，可回源核对。

   两者是**分工，不是二选一** —— 文档给要件与出处，基准给可运行的形状；
   文档可能滞后于版本，所以形状以能跑的实现为准。重点看四样：
   ① `extension.js` 的顶层字段；② `character/character.js` 末尾的 `packs` 结构；
   ③ `characterSort` / `characterSortTranslate` 的写法；④ 头像文件的命名与规格。
2. **定技能**：按「四层退让」逐个零件找现成实现（见 SKILL.md 的策略哲学）
3. **写代码** → `node --check` → `node scripts/check-extension.mjs <扩展目录> <引擎源码根>`

3.5 **过避坑清单**（不能省，也不等于静态检查）：打开 `references/无名杀避坑清单.md`，
   对照末尾「三、根因分类」逐条自问一遍。

   **为什么必须人（模型）过，而不是交给脚本**：脚本查的是**结构**（文件在不在、字段配没配对、
   API 存不存在），下面这些是**语义**，它看不见：
   - `ai` 写没写、写得对不对（脚本只能查"缺不缺"，查不了"合不合适"）
   - `onremove` 里的牌是**归还**还是**丢弃**（脚本只能查到"有 onremove"）
   - `filterCard` / `mod.*` 的入参会不会不是实体牌（要 `typeof card.hasGaintag === "function"` 防御）
   - `cost` 在主动技路径上不执行（运行时行为，静态查不出）
   - 平局分支：`result.bool` 与 `result.tie` 是不是都处理了
   - `event.getParent(n)` 的层数对不对（借来的技能层数可能变）
4. **素材归位**（工坊交上来的文件，文件名**全都不对**，一律用脚本改，别手工改）：

   ```
   python3 scripts/place-assets.py <扩展目录> --char <角色id> --skill "技能名=技能id"
   ```

   **用户直接丢来大图时先裁**：`python3 scripts/crop-avatar.py <原图> <输出.jpg> [--center 0.5,0.35]`
   —— `350×464` 是通行规格（引擎不校验尺寸，超了会拉伸）。走网页工坊的话不用它，工坊右栏自带裁剪器。

   名字必须这么叫，引擎写死的：立绘 `<扩展目录>/<角色id>.jpg`，
   配音 `<扩展目录>/audio/<技能id>1.mp3`、`<技能id>2.mp3`（序号对应技能 `audio` 的数字）。
   而工坊下来的是 `avatar-submitted.jpg`、`audio/霜刃配音-mv22mnokg.mp3` ——
   技能名是中文、id 是英文。**漏改或改错不会报任何错**，只是立绘不显示、配音不响，
   表现为「加了没效果」。脚本会一并提醒技能上的 `audio` 字段该怎么写。
5. **打包** → `python3 scripts/pack-extension.py <扩展目录>`（Windows 用 `python` 或 `py`）
6. **装机（默认要做，不是可选项）** → `python3 scripts/install-to-game.py <扩展目录> <游戏根>`
   - 游戏真正加载的是 `<游戏>/resources/app/extension/<扩展名>/`：
     **工作区里改得再对，不装进去，游戏里看到的还是旧版**（曾因此做过一轮无用功）。
   - 备份自动落在 `extension` 同级的 `extension-backup/` —— **绝不能放进 `extension/` 里面**，
     游戏会把每个子目录都当成一个扩展扫出来，凭空多出一堆垃圾条目。
   - 装完逐个比 sha256（覆盖失败通常不报错）。用户没说游戏在哪就先问（阶段 0 的「找无名杀」）。
7. **自定义势力要注册**：`groupCustom` 非空时，在 `content` 里生成
   `game.addGroup(势力id, "简称", "全名", { color: "#rrggbb" })`（写法与出处见
   `references/无名杀规范.md` 7.4）；颜色按势力气质挑一个，别省略。
   角色 `group` 写这个 id。

### 阶段 4 · 汇报

**总原则：短、说人话、武将放最前。** 跟武将无关的一律放最后一节。
对方多半不懂技术 —— 别说「落盘 / JSON / 静态检查 / 运行时」，用下面的词表。

```markdown
## <武将名> 做好了

<势力>｜<体力>｜<称号>

技能（原文照录，一字不改）：
- <技能名>：<描述原文>

## 拿到手怎么用

- 压缩包（拖进游戏的「扩展」页就行）：`<完整位置>`
- 想留着自己改的源文件：`<完整位置>`
- 进游戏后在「扩展」里打开它，建房间时就能选到这个武将

## 我替你定的事

- <没问过就自己定的，一条一句话；没有就整节省略>

## 其他（跟武将无关）

- <缺环境 / 工具问题 / 文档建议…；没有就整节省略>
```

**必须写**：压缩包的完整位置（能直接复制粘贴）、替用户定的事。
**不要写**：实现依据表、代码结构讲解、「我理解你的需求是…」式复述、
检查项逐条罗列（一句「自动检查过了，没发现问题」就够）。
**宁可少写**：说清了就停，别为了显得完整而堆字。

> **没给立绘，必须提醒一句**（这项常被漏）：
> 「这次没做立绘 —— 不影响玩，但选将时牌面是空的。想要的话补一张
> 350×464 的图片给我，或者下次用网页工坊裁一张。」
> 用户明确说过「不要立绘」时照做，不用再劝。

#### 说人话对照表（写完汇报自查一遍）

| 别写 | 改成 |
|---|---|
| 落盘 / 写入 JSON | 已经存好了 |
| 静态检查 / 语法错误 | 自动检查过，没写错 |
| 运行时崩溃 / 报错 | 在游戏里会出问题 |
| 引擎 / API / 字段 | 游戏本身 / 游戏里的写法 |
| 校验通过 | 检查过，没问题 |
| 打包 / 生成 zip | 做成游戏能装的压缩包 |
| 已导出 | 放在这个位置：`<完整位置>` |

**反过来：这几个概念不用回避** —— 硬绕开反而讲不清，用户会以为你在敷衍：

| 场景 | 必须讲清的概念 | 别这么绕 |
|---|---|---|
| 「联机时别人看不到我的立绘」 | **立绘是每台电脑各自显示的**，你本机有、不等于别人的也有；对方也要装这个扩展包 | 「立绘没生效」（错 —— 本地是好的，会把人带偏） |
| 「联机时技能没反应」 | **联机的游戏逻辑在房主那边跑**，建房的那一方必须装这个扩展 | 「可能是网络问题」（错 —— 多半是没装） |
| 「联机能不能玩」 | 数值型、选择型技能**没问题**；重度依赖动画的**建议先试一局** | 只说「能的」（漏掉真实差异） |

**判断标准**：

- 用户**会自己搜**的词（联机、房主、扩展、立绘）→ **直接用**，换成别的反而听不懂
- 用户**不会搜、但不理解就听不懂结论**的机制（各电脑各自显示、逻辑在谁那跑）→ **讲概念，别用行话**
  （说「每台电脑各自显示」而不是「渲染是客户端本地的」—— 意思一样，后者白加两个行话）

**顺序固定的理由**：用户每次关心的都是同一组事（武将什么样、怎么装进游戏、替他定了什么）。
固定顺序即不漏项，也不会让杂事挤到前面。

> **绝对位置不许省**：只写文件名等于没说 —— 工作区可能嵌得很深，
> 光说「已打包成 我的扩展.zip」，用户还得自己去找。

## 场景 B：用户直接在对话里提需求

没有工坊提交时，阶段 1 略过，其余照走（**阶段 0 的查环境照做**）。
**但需求收集要在对话里做全**：

1. 武将名 / 称号 / 势力 / 性别 / 体力
2. 每个技能的**名字**与**描述原文**（让用户照着念，别自己总结）
3. **明确问**：触发时机、频率、目标、数值边界
4. 要不要立绘（对话里给不了图片时，先做无立绘版本）
5. **用户直接发来一张图** → 先判断是哪一种，应对规则见 `references/卡面识别.md`：
   - **卡面**：直接读图识别，**把结果复述一遍让他核对**，再检查还缺什么
   - **纯立绘原图**：不进识别，直接进裁剪流程，同时**提醒他再补一张卡面图**（或口述设定）
   - 两种都要顺带确认立绘有没有 —— 卡面上的立绘被字挡住，得单独发一张

**需求不清时不要动笔** —— 写完再改比先问清楚贵得多。

## 常见失误（本规范要防的）

| 失误 | 后果 | 防法 |
|---|---|---|
| 没查环境就开工 | 写到打包那步才卡住，用户空等 | 阶段 0 |
| 缺依赖却自行绕过（改系统、猜测命令） | 环境被破坏，问题更难定位 | 阶段 0：停下来让用户装 |
| 没开工坊、没给网址 | 用户不知道有这入口，只能干等 | 阶段 0 末节 |
| 没给立绘却没说 | 用户进游戏发现是空白牌面，回头返工 | 阶段 4 立绘提醒 |
| 没读 JSON 就开始写 | 自己编需求 | 阶段 1 第 1 步 |
| 拿了几天前的提交 | 做的不是当前需求 | 阶段 1 第 2 步 |
| 扩展重名没发现 | 覆盖别人的扩展 | 阶段 1 第 4 步 + `check-extension` |
| 歧义挤牙膏式提问 | 用户被问烦，还得来回好几轮 | 阶段 2：一次性问完 |
| 反过来复述需求求确认 | 伪阻断，用户觉得啰嗦 | 阶段 2 最后一条 |
| 汇报堆术语、写成长文 | 用户看不懂，抓不到重点 | 阶段 4 总原则 + 词表 |
| 跟武将无关的事混在说明里 | 重点被淹没 | 阶段 4：其他事单列最后 |
| 汇报只说"做完了" | 用户不知道检查到什么程度 | 阶段 4 固定顺序 |
| 自己替用户决定的事没说 | 用户事后才发现被改过 | 阶段 4「我替你定的事」 |
